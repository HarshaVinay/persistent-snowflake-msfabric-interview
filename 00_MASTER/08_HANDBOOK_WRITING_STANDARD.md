# Handbook Writing Standard

## Purpose
Keep every note concise enough to revise but deep enough to survive a technical follow-up.

## Standard document format
```text
# Topic

## Curriculum coverage
## Priority
## Mental model
## Core concepts
## Example / code
## Interview answer
## Follow-up questions
## Scenario questions
## Common mistakes
## Project connection
## Evidence and sources
## Last reviewed
```

## Answer standard
For a concept question:
**definition → mechanism → example → why/when**

For a comparison:
**dimension → option A → option B → trade-off → selection rule**

For a coding question:
**clarify → solution → edge cases → complexity → explain aloud**

For a scenario:
**requirements → volume/SLA → design → quality → failure recovery → security → monitoring → cost/performance**

## Evidence standard
Never call a C prediction a verified interview question. Never claim hands-on experience that the project/source does not prove.

## Vendor accuracy standard
Vendor behavior must be described for the relevant product/version. Avoid universal statements that are only true for one database or platform.

## Revision tags
Use:
- `P0` = must know cold
- `P1` = important
- `P2` = supporting
- `A/B/C/D` = evidence confidence
